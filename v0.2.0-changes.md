# v0.2.0 changes

## Goals and constraints

- Make the library `no_std` and allocation-free at runtime.
- Have no external normal, build, or development dependencies.
- Retain `src/books.json` as the canonical source of Bible data.
- Parse and validate the JSON at build time. Do not parse JSON or build an
  index at runtime.
- Keep short book IDs such as `"ge"` only as source-data identifiers. Do not
  expose them through the public API.
- Provide an infallible, no-argument `random_verse` backed by a
  concurrency-safe global ChaCha20 PRNG.
- Support `wasm32-unknown-unknown` without requiring threads, allocation, or
  host-provided entropy.
- Conditionally provide C `cdylib` and `staticlib` artifacts without adding
  FFI items to the Rust public API.
- Relicense the complete project under CC0-1.0.

This is a pre-1.0 breaking release. The public API changes are listed below.

## Cargo configuration

Set the package version to `0.2.0`, use Edition 2024, and declare Rust 1.98.1
as the MSRV. All v0.2.0 build modes are verified with that exact toolchain.

```toml
[package]
version = "0.2.0"
edition = "2024"
rust-version = "1.98.1"
license = "CC0-1.0"
include = [
    "Cargo.toml",
    "build.rs",
    "src/**",
    "include/**",
    "README.md",
    "LICENSE",
]

[lib]
crate-type = ["rlib"]

[profile.capi]
inherits = "release"
panic = "abort"
```

There is deliberately no public C-API Cargo feature. The explicit C-artifact
build described below uses a project-private configuration flag and adds no
public Rust items. There are no `getrandom`, `rand`, Serde, or JSON parser
dependencies, including `rand_core`. The crate does not obtain entropy from
the operating system.

The library root uses:

```rust
#![no_std]
#![deny(unsafe_code)]
#![deny(unsafe_op_in_unsafe_fn)]
```

The private C module is the only exception to `deny(unsafe_code)`, solely
because Edition 2024 classifies `no_mangle` as an unsafe attribute:

```rust
#[cfg(ja_colloquial_c_artifact)]
#[allow(unsafe_code)]
mod c_api;
```

The module contains no unsafe blocks or unsafe operations. Its only unsafe
constructs are reviewed `#[unsafe(no_mangle)]` attributes.

Guard the artifact-only mode at the crate root:

```rust
#[cfg(all(ja_colloquial_c_artifact, not(panic = "abort")))]
compile_error!("C artifacts require panic=abort");
```

`ja_colloquial_c_artifact` is a project-private configuration flag, not a
public Cargo feature. A normal Rust dependency therefore cannot accidentally
enable the C module or include its panic handler in an `rlib`.

Cargo ignores a dependency's profile settings, which is desirable for normal
Rust consumers. The custom `capi` profile leaves ordinary debug and release
`rlib`s unchanged. The C instructions build the unpacked package as the root
package, so `capi` applies there; the crate-root guard rejects any C-artifact
invocation using a profile that does not set `panic = "abort"`.

## Build-time data generation

Add a dependency-free `build.rs`. A build script runs on the host and may
use the Rust standard library even though the library itself is `no_std`.

The build script must:

1. Emit `cargo:rerun-if-changed=src/books.json`.
2. Emit `cargo:rerun-if-changed=include/ja_colloquial.h`.
3. Emit `cargo::rustc-check-cfg=cfg(ja_colloquial_c_artifact)` so rustc's
   configuration checking recognizes the private artifact-mode flag.
4. Read `src/books.json`.
5. Parse its fixed JSON schema with a small parser implemented in `build.rs`.
6. Validate the complete input.
7. Write generated Rust constants to `$OUT_DIR/verses.rs`.
8. Write the expected C header to `$OUT_DIR/ja_colloquial.h`.
9. Compare it byte-for-byte with `include/ja_colloquial.h`; fail with the
   generated path and an instruction to update the checked-in header if they
   differ.

Do not make `build.rs` guess the requested crate type. Rust 1.98.1 exposes no
stable crate-type `cfg` or build-script environment variable, and
`rustc --print cfg` does not distinguish `rlib`, `staticlib`, and `cdylib`.
The explicit C-artifact command supplies `ja_colloquial_c_artifact` directly
to the final crate compilation.

The custom profile cannot be the condition either. Cargo 1.98.1 does not
support `crate-type` in a profile, and a build script sees `PROFILE=release`
for `capi` because it inherits `release`; Cargo intentionally reduces this
variable to `release` or `debug`. Do not parse the profile name out of
`OUT_DIR`, whose layout is not an interface. Keep profile selection, crate-type
selection, and the private cfg explicit in the one documented command.

`src/verses.rs` includes the generated file:

```rust
include!(concat!(env!("OUT_DIR"), "/verses.rs"));
```

Do not try to parse the contents of `include_str!("books.json")` with
`macro_rules!`; declarative macros cannot inspect a string literal's
contents.

The parser only needs to accept the schema used by `books.json`, but it must
handle all standard JSON string escapes, including valid UTF-16 surrogate
pairs in `\u` escapes, or reject malformed input with a precise build error.
Generated Rust C string literals must be escaped correctly.

The generated file contains:

- one flat `VERSES` array;
- one flat `CHAPTERS` array;
- one `BOOKS` array;
- one `BOOK_NAMES` array;
- a generated Japanese-book-name-to-index lookup;
- one public `const BIBLE: Bible` value.

The generator must validate:

- every object has exactly the required `b`, `c`, `v`, `jb`, and `t`
  fields;
- each distinct book ID forms one contiguous book and has one consistent
  Japanese name;
- Japanese book names are unique after applying the documented source-data
  correction;
- `(book ID, chapter, verse)` tuples are unique;
- books and chapters are grouped and ordered consistently;
- chapter numbers start at 1 and are contiguous within each book;
- verse numbers are positive and strictly increasing within each chapter;
- all indices and numeric fields fit their generated integer types;
- verse text is nonempty;
- Japanese names and verse text contain no embedded NUL bytes;
- the data contains at least one verse.

Verse numbers are not required to be contiguous. The current source has 16
discontinuities covering 17 absent verse numbers. For example, Numbers 15
jumps from verse 3 to verse 5. Preserve these gaps instead of renumbering
verses or inserting synthetic records.

The current source is expected to generate 66 books, 1,189 chapters, and
31,086 verse records. Pin these totals in tests so accidental truncation is
detected.

## Internal representation

Use a flat verse array and compact range metadata:

```rust
pub struct Bible {
    verses: &'static [Verse],
    books: &'static [Book],
    chapters: &'static [Chapter],
    book_names: &'static [&'static str],
}

struct Book {
    first_chapter_idx: u16,
    chapter_count: u8,
}

struct Chapter {
    first_verse_idx: u16,
    // Number of records, not the highest verse number.
    verse_count: u8,
}

#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash)]
struct Text {
    rust: &'static str,
    c: &'static core::ffi::CStr,
}

impl Text {
    const fn new(c: &'static core::ffi::CStr) -> Self {
        let rust = match c.to_str() {
            Ok(text) => text,
            Err(_) => panic!("generated verse text is not UTF-8"),
        };
        Self { rust, c }
    }
}

#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash)]
pub struct Verse {
    text: Text,
    book_idx: u8,
    chapter: u8,
    verse: u8,
}
```

Build-time checks must prove that the selected integer widths are sufficient.
Do not rely on Rust's default field order as a stable layout guarantee.

A `Chapter` identifies a contiguous slice of the flat verse array. Exact
verse lookup searches that slice by the stored verse number, preferably using
binary search. It must not calculate `first_verse_idx + verse - 1`, because
the source contains verse-number gaps.

Book lookup by Japanese name is generated from `books.json`, not handwritten.
Short book IDs are used only while parsing and validating the source. Unknown
book names return `None`.

## Public API

```rust
pub use verses::BIBLE;

impl Bible {
    /// All verse records in source order.
    pub fn verses(&self) -> &[Verse];

    /// Japanese book names in source order.
    pub fn book_names(&self) -> &[&str];

    /// Number of chapters in `book_name`.
    pub fn chapter_count(&self, book_name: &str) -> Option<usize>;

    /// All records in a chapter, ordered by verse number.
    pub fn chapter(
        &self,
        book_name: &str,
        chapter: usize,
    ) -> Option<&[Verse]>;

    /// Number of records present in a chapter, not necessarily the highest
    /// verse number.
    pub fn verse_count(
        &self,
        book_name: &str,
        chapter: usize,
    ) -> Option<usize>;

    /// Looks up an exact 1-based chapter and verse number.
    ///
    /// Returns `None` for an unknown name, zero, an out-of-range number, or a
    /// verse number absent from the source.
    pub fn verse(
        &self,
        book_name: &str,
        chapter: usize,
        verse: usize,
    ) -> Option<Verse>;

    /// Uniformly selects one record using the crate-global PRNG.
    pub fn random_verse(&self) -> Verse;
}

impl Verse {
    pub fn book_name(&self) -> &'static str;
    pub fn chapter(&self) -> usize;
    pub fn number(&self) -> usize;
    pub fn text(&self) -> &'static str;
}

/// Installs a 128-bit key and resets the crate-global PRNG sequence.
pub fn seed(seed: [u8; 16]);
```

The generated module defines the public `BIBLE` constant using the generated
static slices, and the library root re-exports it as shown above. `BIBLE` is
sufficient because `Bible` contains only immutable references to generated
`'static` arrays. No `bible()` accessor function is provided.

`Bible` and `Verse` fields remain private. This keeps the representation
changeable and removes the abbreviated v0.1 fields `b`, `c`, `v`, `jb`, and
`t` from the public API.

`random_verse` is infallible because the generated `BIBLE` is validated as
nonempty.

Generate each verse as `Text::new(c"...")`. The C string literal supplies one
NUL-terminated allocation, and the const constructor derives a UTF-8 `str`
view excluding the terminator. `Verse::text()` returns `text.rust`; a private
crate-only accessor returns `text.c` to the C module. Both slices point into
the same static bytes, so this neither duplicates the approximately 8 MB text
corpus nor repeats UTF-8 validation at runtime. The build script's UTF-8 and
embedded-NUL checks remain mandatory rather than relying only on literal or
const-evaluation failures.

## C ABI

The C ABI is implemented in the private `src/c_api.rs` module and is compiled
only when `ja_colloquial_c_artifact` is set. Nothing in the module is `pub` or
re-exported as a Rust item. Edition 2024 still requires private exported
functions to use `#[unsafe(no_mangle)]`; that attribute exports their linker
symbols even though they are invisible through the Rust API.

The C-artifact build defines one `#[cfg(not(test))]` panic handler which never
unwinds (for example, a spin loop). It does not define a panic handler while
compiled as a test harness. This handler is why the C-artifact invocation must
not also emit an `rlib`: panic handlers are compiler lang items, not ordinary
mangled symbols, and such an `rlib` would conflict with a Rust executable's
panic implementation.

```rust
#[cfg(not(test))]
#[panic_handler]
fn panic(_: &core::panic::PanicInfo<'_>) -> ! {
    loop {
        core::hint::spin_loop();
    }
}
```

The C ABI must not require callers to pass pointers. This permits its complete
implementation in safe Rust apart from the required `unsafe(no_mangle)` symbol
attributes. Every exported symbol must have a safety comment stating that its
globally unique `ja_colloquial_` prefix prevents symbol collisions.

### Header

Check in `include/ja_colloquial.h` as the C API contract. It must be valid
C99 and C++, include `<stdint.h>`, use include guards, and wrap function
declarations in `extern "C"` when compiled as C++.

Books are represented only by C `int` values. The header defines:

```c
typedef int ja_colloquial_book_t;

#define JA_COLLOQUIAL_BOOK_GENESIS ((ja_colloquial_book_t)0)
/* ...all 66 books in canonical source order... */
#define JA_COLLOQUIAL_BOOK_REVELATION ((ja_colloquial_book_t)65)
```

Use full ASCII English identifiers for these macros. Do not expose the JSON

The returned verse type is:

```c
typedef struct ja_colloquial_verse {
    ja_colloquial_book_t book;
    int chapter;
    int verse;
    const char *text;
} ja_colloquial_verse_t;
```

`text` is UTF-8, NUL-terminated, valid for the lifetime of the program, and
must never be freed or modified. A null `text` denotes an invalid lookup.

The header declares:

```c
void ja_colloquial_seed(uint64_t a, uint64_t b);
int ja_colloquial_book_count(void);
int ja_colloquial_book_chapters(ja_colloquial_book_t book);
int ja_colloquial_chapter_verses(ja_colloquial_book_t book, int chapter);
ja_colloquial_verse_t ja_colloquial_get_verse(
    ja_colloquial_book_t book,
    int chapter,
    int verse
);
ja_colloquial_verse_t ja_colloquial_random_verse(void);
```

Count functions return `-1` for invalid arguments. `ja_colloquial_get_verse`
returns `{ -1, 0, 0, NULL }` for an invalid book, chapter, verse, or a verse
number absent from the source. `ja_colloquial_random_verse` always returns a
valid record.

`ja_colloquial_seed(a, b)` constructs the Rust `[u8; 16]` seed by placing
`a.to_le_bytes()` first and `b.to_le_bytes()` second. This specifies identical
seed behavior on little- and big-endian systems.

## Global random number generator

Implement the PRNG in `src/random.rs` using atomics from
`core::sync::atomic`. Do not use thread-local storage, `static mut`, unsafe
code, allocation, or `std`.

Use the original 128-bit-key ChaCha20 construction:

- the constants spell `"expand 16-byte k"`;
- the four little-endian key words are repeated to fill the eight key words
  in the ChaCha state;
- use 20 rounds;
- use the original 64-bit-counter/64-bit-nonce state layout;
- keep the 64-bit nonce fixed at zero;
- keep the high 32 bits of the block counter at zero and atomically allocate
  the low 32 bits.

This deliberately limits one seed to fewer than 2^32 64-byte blocks. Counter
exhaustion must panic with a clear message instead of wrapping and reusing a
ChaCha block. Calling `seed` installs a new key and resets the block counter.

The initial key is all zeroes. This makes `random_verse` usable before
explicit seeding and gives reproducible default behavior, but it is publicly
predictable. Cryptographic unpredictability is provided only after the caller
supplies an unpredictable `[u8; 16]` seed.

### Atomic state and reseeding

Require `cfg(target_has_atomic = "32")`. Store the state as:

```rust
static EPOCH: AtomicU32 = AtomicU32::new(0);
static KEY: [AtomicU32; 4] = [const { AtomicU32::new(0) }; 4];
static BLOCK_COUNTER: AtomicU32 = AtomicU32::new(0);
```

`EPOCH` is a sequence lock. An even value means the key is stable; an odd
value means a writer is installing a seed.

Use `Ordering::SeqCst` for every access to these atomics. The operation rate is
tiny compared with ChaCha generation and verse lookup, and a single total
order makes the reseeding proof substantially easier to audit. Do not weaken
the ordering without a separately reviewed memory-model proof.

`seed` must:

1. acquire the writer position by changing an even epoch to the following odd
   value with compare-and-exchange;
2. decode and store the four little-endian seed words;
3. reset `BLOCK_COUNTER` to zero;
4. publish the following even epoch.

Never wrap `EPOCH`. Refuse to reseed and panic before the next pair of epoch
increments would overflow. This excludes the sequence-lock ABA case after
2^31 reseeds.

Random generation must:

1. load an even epoch;
2. snapshot the four key words;
3. reserve one block counter without permitting wrap;
4. load the epoch again;
5. discard the reservation and retry if the epoch changed;
6. generate the ChaCha20 block from the accepted key/counter pair.

This makes reseeding and generation data-race-free without an unsafe interior
mutable value. A random call that overlaps reseeding may consume and discard a
counter, which is harmless. Every accepted call receives a unique key/counter
pair until exhaustion or reseeding.

Calling `seed` concurrently with generation is memory-safe, but the order in
which old-key and new-key outputs are returned is unspecified. Reproducible
callers must ensure reseeding does not race with generation.

If counter reservation reports exhaustion, recheck `EPOCH`: retry when a
concurrent reseed changed it, and panic only when the same stable epoch is
still current. This avoids a spurious exhaustion panic while another caller
is installing a fresh key.

### Unsupported targets

If 32-bit compare-and-swap atomics are unavailable, fail with a clear
`compile_error!`. Supporting concurrent global mutation there would require
unsafe target-specific assumptions or another synchronization dependency,
both outside this release's constraints.

Both `wasm32-unknown-unknown` and `wasm32v1-none` currently expose 32-bit
atomic APIs through `core`, including when the WebAssembly runtime has no
threads, so both targets are supported.

### Private random interface

Do not expose an RNG type or implement an external RNG trait. The crate only
needs private functions which reserve a block and return the required random
word, plus the bounded-index function used by `random_verse`:

```rust
fn next_u64() -> u64;
fn random_index(upper: usize) -> usize;
```

The ChaCha block function remains separately testable. Do not add a general
word or byte-filling API unless another internal caller actually needs it.
Each `next_u64` call reserves one ChaCha block, uses its first eight bytes in
little-endian order, and discards the rest. This deliberate inefficiency
avoids a second layer of shared mutable cache state. The public
`seed([u8; 16])` function is the only state-management API.

Do not claim an unconditional cryptographic RNG trait: the state has a public
all-zero initial key and may be given a predictable key. The ChaCha20 stream is
a CSPRNG only after the caller supplies an unpredictable seed and keeps it
secret.

The implementation is security-sensitive despite its small size. Keep the
ChaCha core separate from atomic state management, avoid data-dependent
branches and table lookups in the core, and document that this in-tree
implementation has not received an independent cryptographic audit.

### Uniform verse selection

Convert random words to an index with rejection sampling or another proven
unbiased bounded-integer algorithm. Do not use
`random % verses.len()` by itself, because that introduces modulo bias.

## Migration from v0.1

- `books()` is replaced by the `BIBLE` constant.
- `Books` becomes `Bible`.
- `Books::get_verse` becomes `Bible::verse`.
- `Books::book_names`, which held short IDs, becomes `Bible::book_names()` and
  now returns Japanese names.
- Short book IDs are no longer exposed or accepted by the public API.
- Public `Verse` fields become accessor methods.
- `Verse::v` becomes `Verse::number()`.
- `random_verse()` remains a no-argument method, but now uses the
  deterministic crate-global PRNG.
- `seed([u8; 16])` installs a 128-bit key and resets that global sequence.
- The single package emits an `rlib` normally. An explicit, conditionally
  compiled artifact mode emits `cdylib` and `staticlib`; its items remain
  absent from the Rust API.
- The project license changes from `Apache-2.0 OR MPL-2.0` to `CC0-1.0`.

Update the README and crate-level documentation with the new API and state
clearly that the default stream is deterministic and that unpredictability
depends entirely on the caller supplying an unpredictable seed.
